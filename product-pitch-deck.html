问题

传统建筑运维，停在「看数据」

系统很多、数据很全，但"看懂 + 决策"仍靠人。三个真实痛点：

痛点 01

看数据 ≠ 会诊断

BI 大屏只展示"温度 82°C 越限"，不回答"为什么、是不是真故障、该怎么处理"。诊断仍靠老师傅经验。

影响 · 响应慢 3h+
痛点 02

告警轰炸

一台冷水机组故障，连锁触发几十条告警，值班被淹没，分不清根因，真故障被埋没。

影响 · 误报率 >60%
痛点 03

经验断层

老专家退休 = 知识带走。新人不会排查、不会看趋势，SOP 躺在手册里没人翻。

影响 · 培训 6+ 月
现状 物业报修"3 楼会议室太热" → 客服转派 → 工程现场判断 → 数小时甚至隔天才有结论 —— 响应慢、依赖人、不可沉淀。

定位

从「看数据」到「问数据 + 让它干活」

用户用自然语言描述问题（哪怕只是"太热了"）， AI 助手自动完成定位 → 诊断 → 建议 → 派单 → 报告，全程可解释、可审计。

入口
01

对话式交互

不翻手册、不看大屏，直接问。模糊表达也能澄清到具体设备。

→ "3楼太热" → AHU-03
内核
02

自动诊断

plan-and-execute 鉴别诊断循环：提假设 → 验证 → 换假设 → 下结论。

→ 假设 → 验证 → 换假设
闭环
03

落地派单

诊断完一键生成工单（人工确认），从"发现问题"到"处理问题"闭环。

楼宇智诊 · 产品立项提案05
核心机制

plan-and-execute：把诊断做成「鉴别诊断循环」

老师傅排查故障不是"照清单跑完"，而是提假设 → 验证 → 证据不符就换假设 → 锁定根因。

场景 A

温度渐进升高 + 散热告警 → 判定「散热器堵塞」，建议维修

场景 B

温度突变回落 + 其它正常 → 换假设「传感器漂移」，不建议派单

价值

一次误派工的代价，远超整套 Agent 的搭建成本

落地

分阶段落地：先打通一条主线

MVP · 交付物
  • ▸ 告警收敛 + 根因定位
  • ▸ plan-and-execute 基础循环
  • ▸ Mock 数据验证闭环
V1 · 交付物
  • ▸ 空间树下钻到具体设备
  • ▸ 自然语言模糊澄清
  • ▸ 真实工单系统对接
V2 · 交付物
  • ▸ 巡检编排 + 证据链
  • ▸ 能碳多因素归因
  • ▸ 知识库 RAG + 报告生成
V3 · 交付物
  • ▸ 全量设备接入
  • ▸ 多楼宇 + 主动预警
  • ▸ 控制下发（审批后）
原则 先打通 报修 → 诊断 → 派单 一条主线，最贴近物业日常、最快见 ROI；再横向扩展巡检 / 能碳 / 知识。
